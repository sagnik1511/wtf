## Resulting behavior

New experiments store private network weights/biases, Q/QR-DQN targets, GRPO
references and Adam moments/variances in four-byte float arrays across all nine
algorithms. Newborn crossover/mutation and champion warm starts retain independent
packed buffers. Arithmetic, transient activations, accumulated gradients, losses,
returns and world health/energy/terrain values remain Python float64. This is a
storage precision change; no Cython/C backend, NumPy/PyTorch dependency or new
build step is introduced. Floating-point rounding can change future policies and
world trajectories for identical seeds compared with the preceding float64 code.

Full checkpoints record each brain's precision and the experiment initialization
precision. Files without those fields retain legacy float64 continuation,
including future children and episodes. Warm-starting old champion weights into
a new float32 experiment rounds them to the new run's precision. Recording run
metadata and champion snapshots describe the precision. JSON-compatible public
snapshots remain detached ordinary values. See [numeric precision](../running.md#numeric-precision).

Binary arrays use float32 only when every source float round-trips exactly;
otherwise they retain float64. Unsigned integer arrays use uint8/uint16/uint32
only when all values fit and their payload is smaller than signed varints.
Negative values, large IDs/seeds and counters retain their existing exact
encodings. Live IDs/ages/generations are not blindly narrowed. Python and JS
readers support the added tags; seeking, event animation, chart values and
independent chunk decoding retain their existing interfaces. See
[binary storage](../binary-storage.md).

## Measurements and verification

A CPython 3.9.6 container-size check with 1,024 independently allocated values
measured 33,432 bytes for a list plus float objects, 8,256 bytes for packed
float64 and 4,176 bytes for the new Float32 buffer. The new numeric payload is
4,096 bytes; its binary array record is 4,099 bytes versus 8,195 for the float64
array. Integer samples `[64,127,128,255]` and `[256,32767,32768,65535]` encode in
6 and 10 bytes respectively, including tag/count. These are container and
uncompressed encoding sizes, not process RSS, compressed-run disk savings or
training throughput measurements. No profiler or long learning experiment ran.

- Full Python suite: **376 passed**.
- JavaScript viewer suite: **50 passed**.
- New precision tests cover all algorithms, packed ownership, births, champion
  loading, legacy float64 optimizer continuation, future episode initialization,
  five checkpoint formats, invalid precision/overflow and actual float32 rounding.
- Binary tests exercise uint8/uint16/uint32 boundaries, float64 fallback, signed
  zero, truncation and Python/JS parity for each new tag.
- Finite-difference checks divide by the actual representable weight perturbation;
  their derivative tolerances remain strict. Learning-rate scaling checks allow
  a float32-sized rounding bound at stored parameters.

## Operation and rollback

Existing commands create float32 runs automatically; configuration JSON files do
not need editing. Existing results are untouched. Restart a running playback
server and refresh its viewer before opening new binary files. Older readers do
not understand the added array tags, so retain updated readers when rolling back
learning code. New float32 checkpoints continue exactly with precision-aware
readers; older code would lose storage-rounding semantics even if exported as
JSON. No commit, tag or package-version change was created.

Native kernels remain a separate possible speed improvement. Packing removes
retained Python number objects, but Python training loops and scalar boxing on
array access remain; no training speedup is claimed.
