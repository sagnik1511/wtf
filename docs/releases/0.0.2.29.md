## Overview

The initial CUDA prototype spent more time than native CPU on the measured T4
workload. This revision changes the execution/data flow: complete ordinary and
masked PPO updates run on GPU, ready independent brains share batched launches,
unchanged weight uploads are cached, and per-sample parameter-gradient tensors
are removed. Optional FP32 is separate from the default FP64 execution contract.
User-provided Kaggle Tesla T4 measurements now establish the scoped speedups
below; no NVIDIA execution was performed on the local Mac.

## Changes

- Cooperative warp dot products read adjacent weights; gradient reduction uses
  saved activations/deltas instead of a full parameter-gradient copy per sample.
- Exact-content weight/target upload caches detect arbitrary in-place edits;
  bounded host staging and device workspaces share eviction lifetimes.
- Private PPO parameters/Adam state remain resident across grouped rollout epochs
  and minibatches, including masks, partial batches, private shuffle RNGs and
  independent KL stopping. Publish CPU snapshots before selection/inheritance.
- Automatic inference retains CPU action evaluation for CUDA-trained PPO/DQN;
  explicit CPU/CUDA action choices remain available for comparisons.
- Explicit FP32 arithmetic and event profiling flags, with benchmark propagation,
  byte counters and profiling-aware suppression of speedup ratios.
- [Colab instructions](../cuda.md#colab-comparison) cover separate FP64/FP32 and
  diagnostic runs, without writing playback/checkpoint artifacts.

## Compatibility and migration

Rebuild `_cuda_dqn.so`: native ABI 1 changes to 2. CPU remains the default and
saved brain/checkpoint/replay encodings remain unchanged. GPU execution choices
are transient and must be selected again after restore. FP32 applies only to GPU
brain computation and can change trajectories; world physics and artifact dtypes
remain unchanged. DQN/DDQN retain their CPU optimizer; other dense policies retain
their existing training paths. No PyPI publication or package-version bump.

## Fixes and optimizations

Independent `wtf-reviewer` review found no actionable implementation defects in
the reviewed scope. CPU-oracle regressions cover private updates, partial batches,
KL stopping and publication before checkpoint/inheritance. Explicit hardware tests
also target native FP64/FP32 execution, including per-animal KL rejection and
unchanged rejected optimizer state, but remain unrun locally.

For 64 networks of layout `[20,64,64,32,10]` and batch size 16, the DQN device-buffer
formula falls from 77,449,792 bytes to 11,569,728 bytes in FP64 (85.06% reduction),
or 7,814,976 bytes with optional FP32 (89.91%). This is analytical allocation
accounting, excluding host caches, CUDA context/driver overhead and events; it is not a measured peak-memory reduction. See the
[CUDA guide](../cuda.md#analytical-device-buffer-footprint) for the scope.

### CUDA v1 to v2: optimization and measured result

V1 offloaded small action calls and materialized per-sample parameter gradients.
V2 keeps default PPO/DQN inference on CPU, batches independent training jobs,
reuses staging and exact-content uploads, reduces gradients from activations/deltas,
and keeps PPO Adam state on-device across minibatches. DQN/DDQN Adam remains on CPU.

| Learner | V1 CPU / CUDA loop, seconds | V2 CPU / CUDA median loop, seconds | V2 median paired speedup |
| --- | --- | --- | --- |
| PPO | 32.721 / 78.386 | 24.394 / 16.563 | 1.44× |
| DQN | 17.066 / 35.288 | 15.025 / 9.560 | 1.55× |
| DDQN | 23.370 / 38.820 | 20.004 / 10.477 | 1.89× |

User-provided Kaggle results on a Tesla T4 ×2 machine (15,360 MiB per GPU),
1,000 requested steps. V1 numbers are initial
single-pair reports; V2 uses FP64, `[64,64,32]` hidden layers and matched seeds
100–102. Speedup is the median of per-seed CPU/CUDA ratios, not the ratio of the
two median times. Separate sessions and sampling prevent treating the V1/V2
absolute times as a controlled revision-only comparison. V2 CPU/CUDA step/update
counts matched; this does not prove identical trajectories. No replay/checkpoint
I/O is timed.

The backend uses one CUDA device per process; it does not distribute one update
across both T4s. The supplied `nvidia-smi` shows the notebook process on GPU 0
and GPU 1 idle. Treat these as single-T4 timings on a dual-T4 host, not dual-GPU
scaling results. GPU memory sampling also targets device 0 only.

With larger `[128,128,64]` brains, V2 paired speedups were 1.88× PPO, 1.84× DQN and
2.22× DDQN. A 32 MiB workspace kept medium-brain timing within approximately 2%
of the 256 MiB budget while substantially reducing retained buffers. Absolute host
RAM in the final notebook has an inherited-rusage floor, corrected in V3.

FP32 made DQN/DDQN slower: host optimizer/unpacking took 7.931/8.476 seconds,
versus only 0.135/0.184 seconds of GPU computation in separate profiled runs.
PPO FP32 changed update counts for one seed, so no clean precision speedup is
claimed. GPU inference alone did not accelerate the other CPU-trained learners;
masked PPO did benefit from its full GPU update path. The final suite completed
132/133 trials; CUDA SAC was interrupted, with no recorded failures among completed
trials. These bottlenecks motivate the [V3 changes](0.0.2.30.md#cuda-v2-to-v3-differences).

## Rollout and rollback notes

Pull the CUDA branch, rebuild native CPU/CUDA kernels, run the real-device suite,
then compare complete loops with profiling disabled. Keep CPU when it is faster.
Revert to the previous checkout and rebuild its matching ABI to compare the
original prototype. Preserve source checkpoints/replays; no conversion is needed.
