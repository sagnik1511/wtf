## Overview

FP32 DQN/DDQN gradient publication spent substantial host time widening individual
values before CPU Adam. The comparison path now widens a whole packed array in
one native loop. The CUDA optimizer path keeps gradients, clipping, Adam and target
synchronization on the GPU, with coherent CPU snapshots at every grouped update.

## Changes

- Add exact optional native FP32-to-FP64 gradient conversion with reusable staging.
- Avoid allocating CPU gradient trees for deferred DQN updates.
- Add DQN/DDQN device Adam and scheduled target updates, retaining private state,
  replay sampling, RNG ownership, grouping safeguards and update counters.
- Cache online/target/Adam contents within bounded workspaces; invalidate after
  changes, slot reuse, eviction or failed native publication.
- Publish CPU weights/moments/variances and loss summaries before selection,
  inheritance, diagnostics and checkpoints. GPU execution never changes readers.
- Expose transient `--cuda-optimizer cpu/cuda`, default cuda when CUDA is selected.
- Prefer Linux `/proc/self/status` VmHWM for benchmark host peaks to avoid inherited
  process-rusage floors in notebook-launched workers.
- Update adaptive architecture diagrams and CPU/GPU comparison instructions.

## CUDA v2 to v3 differences

| Boundary | V2 (`bdf213d` / `f8de32f`) | V3 (`dc91fbd`) |
| --- | --- | --- |
| FP32 gradients with CPU Adam | Per-value Python widening during unpacking | Exact bulk native widening into reusable FP64 storage |
| DQN/DDQN optimizer | Download gradients; CPU clipping, Adam and target updates | Default GPU clipping, private Adam and target updates; CPU comparison remains selectable |
| CPU-visible state | CPU Adam owns the latest weights/moments | Bulk-publish coherent weights/moments/variances after each grouped device update |
| Deferred gradients | Allocate a CPU gradient tree before queuing | Omit the unused tree on the resident path |
| Benchmark host RAM | Process rusage can inherit a notebook-parent peak | Prefer Linux post-exec VmHWM |
| Native CUDA ABI | 2 | 3; rebuild required |

The [V2 release](0.0.2.29.md#cuda-v1-to-v2-optimization-and-measured-result) holds
V1→V2 performance evidence. V3 keeps both optimizer placements for direct comparison.

### Kaggle T4 optimizer comparison

User-provided V3 results: Kaggle Tesla T4 ×2 host, one GPU used per process,
Python 3.13.16, `[64,64,32]` hidden layers, 1,000 steps, seeds 100–102, automatic
CPU inference, 32 MiB workspace and profiling disabled. All 30 trials completed;
per-seed step/update counts matched across placements and precision modes.

| Learner / arithmetic | CPU Adam median loop | GPU Adam median loop | Paired GPU-Adam speedup | Highest host RAM peak, CPU / GPU Adam |
| --- | --- | --- | --- | --- |
| DQN / FP64 | 9.624 s | 9.291 s | 1.051× | 192.0 / 191.3 MiB |
| DQN / FP32 | 8.637 s | 9.163 s | 0.948× | 216.1 / 201.5 MiB |
| DDQN / FP64 | 10.790 s | 9.649 s | 1.118× | 191.0 / 190.7 MiB |
| DDQN / FP32 | 9.173 s | 9.557 s | 0.963× | 215.4 / 201.1 MiB |

Both columns use V3: CPU Adam already includes bulk native widening, so this is an
optimizer-placement comparison, not an old-V2/new-V3 pair. Ratios are medians of
per-seed ratios rather than ratios of median times. GPU Adam reduced FP64 time by
4.8% for DQN and 10.6% for DDQN; it increased FP32 time by 5.5% and 3.9% respectively.
These are three matched worlds, not repeated measurements of timing noise.

The fastest tested configuration was FP32 CUDA computation with **CPU Adam**:
8.637 s DQN and 9.173 s DDQN, with paired 1.745×/2.167× speedups over fully CPU
training. FP64 GPU Adam achieved 1.646×/2.103× overall speedups. In FP32, GPU Adam
used 14.6/14.3 MiB less highest observed host RAM but was slower. GPU-memory peaks
were not supplied. Linux VmHWM also corrects V2's inherited host-RAM floor; lower
CPU peaks around 50 MiB are not evidence of an equivalent allocation reduction.

Keep placement configurable: FP64 favors GPU Adam here; FP32 favors bulk widening
plus CPU Adam. No default changes follow from these measurements. Matching work
counts does not establish identical trajectories or learning quality. GPU numerical
regression-test output remains separate from successful benchmark execution; no
replay/checkpoint I/O is timed. Further profiling is needed to attribute the remaining
FP32 GPU-Adam cost to device optimizer work versus snapshot publication.

## Compatibility and migration

Rebuild both optional native CPU and CUDA extensions. CUDA ABI 3 explicitly rejects
older shared libraries. Old CPU extensions without the widening helper retain their
conversion fallback. CPU remains the default; artifact formats, simulation physics,
viewer behavior and saved-model contracts are unchanged. Device clipping/Adam use
double arithmetic and FP32 storage; optional FP32 forward/backward remains configurable.
CUDA rounding can differ from earlier device/CPU execution; bit-identical GPU
trajectories are not guaranteed. Restored checkpoints start on CPU and need explicit
CUDA selection. No package-version bump or publication is performed.

## Fixes and optimizations

Independent `wtf-reviewer` inspection found no further actionable defects in the
reviewed runtime scope. Verified safeguards include grouping by optimizer settings,
private update counters and target cadence, exact-content invalidation after slot
changes/host edits, failure cache invalidation, and publication before champion
selection, offspring inheritance and checkpoint reads. Deferred updates omit unused
CPU gradient trees while the ordinary CPU allocation/sampling order is preserved.

The optional bulk widening helper preserves gradient bytes exactly and validates
buffer widths/types before writing. The developer's 64-model host unpacking
measurement was 15.295 ms → 0.455 ms (33.6×); an independent repeat measured
16.489 ms → 0.557 ms (29.6×), also byte-identical. These are isolated host-path
measurements, not full-loop GPU speedups. Linux benchmark host peaks now prefer
post-exec VmHWM rather than inherited rusage history.

Changed-file Pylint 4.1.4 passed with exit zero. The independent targeted suite
completed 70 tests successfully, with five explicit NVIDIA tests skipped. Existing
narrow argument/complexity suppressions keep ABI/state-publication operations
inspectable; no blanket suppressions were introduced. No additional fixes or owner
decisions remain from this review. Local CUDA execution is unavailable. Subsequent
user-provided Kaggle outputs confirm V3 compilation and successful benchmark
execution, including resident optimizers. The numerical hardware-regression suite
results and GPU-memory measurements have not been supplied.
